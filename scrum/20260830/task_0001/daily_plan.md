# Task 0001 daily product-building plan

This is a 35-project-day main sequence plus a four-session parallel companion-app track (B1–B4, inserted 2026-08-31 per [ADR 0007](../../../docs/decisions/0007_use_companion_app_and_cloud_history_sync.md) and the [companion app and synchronization architecture](../../../docs/design/0002_companion_app_and_sync_architecture.md)). One project day is a focused session; it need not equal a calendar day, and shipping pauses do not consume days. Record actual dates, orders, measurements, links, and deviations in a `daily_log.md` when execution starts. A failed exit condition pauses downstream purchases.

Execution note (2026-08-31): Day 1's recorded purchase deviated from this plan—the full CoreS3 K128 was bought instead of the Lite. The plan remains as the historical intent; use the [daily log](daily_log.md) and [ADR 0001 amendment](../../../docs/decisions/0001_use_esp32s3_interaction_mule.md) as the actual record. Later generic “CoreS3 Lite” bring-up steps apply to the purchased K128 unless a variant-specific difference is explicitly noted.

## Milestone 1 — Prove the experience before hardware complexity

### Day 1 — Freeze the experiment and place the only immediate order

- **Build/test:** Read the product concept and requirements, choose three representative conversations with overlap/interruption cases, create a separate OpenAI API project with billing/usage alerts, enforce a hard application quota in the gateway, and try the voice/persona, semantic VAD, and interruption behavior in the [Realtime Playground](https://platform.openai.com/playground/realtime).
- **Purchase/decision:** Order exactly one M5Stack CoreS3 Lite and one known-good data-capable USB-C cable. **Buy the CoreS3 Lite from [DigiKey (part 27689559)](https://www.digikey.com/en/products/detail/m5stack-technology-co-ltd/K128-LITE/27689559), not from M5Stack direct or Amazon** — there is no Amazon listing for the Lite, and M5Stack ships from Shenzhen in 1–3 weeks against DigiKey's next business day to New York (see the NY sourcing section of the [BOM](../../../docs/research/0001_component_sources_and_bom.md)). Record landed cost and ETA. Do not buy cellular, a final battery, or a display.
- **Why:** An integrated mule removes wiring variables while software and interaction are still changing. The Playground tests the highest-risk subjective question immediately.
- **Exit evidence:** Versioned prompt/voice notes, three saved evaluation scripts, receipt, and an explicit API spend ceiling.

### Day 2 — Make a desktop full-duplex voice slice

Implementation note (2026-08-31): V1-A starts with the current unified browser-WebRTC flow and a localhost session broker because it is the shortest beginner path and still keeps the standard key server-side. It is an interaction reference harness, not a change to ADR 0003's product gateway. The server-to-server WebSocket adapter remains the embedded/product transport work after the browser behavior is proven.

- **Build/test:** Implement the smallest desktop/browser path that continuously captures while returned audio plays. For V1-A, let WebRTC carry the independent input/output media and let a localhost session broker combine the browser's SDP with server-owned configuration at `/v1/realtime/calls`; keep the standard API key only in that broker. Configure semantic VAD and exercise WebRTC-managed speech interruption/truncation. Subscribe to `response.output_audio_transcript.delta`/`.done` and render a first sliding caption in the desktop client, trimming its queued unheard tail on interruption. This desktop caption stages PR-07 but does not pass its on-device gate. Build and compare the product gateway's server-to-server WebSocket adapter after this interaction reference works.
- **Purchase/decision:** Buy nothing. Select `gpt-realtime-2.1-mini` as the configurable development baseline and `gpt-realtime-2.1` as the quality comparator.
- **Why:** It proves credentials, provider events, audio format, and model behavior without embedded debugging. A configurable comparison avoids confusing model quality with device quality.
- **Exit evidence:** One recorded button-opened live session with speech during assistant output, a cancellation/truncation trace, timing breakdown, and proof the client bundle/logs contain no standard provider key.

### Day 3 — Prototype the face on a PC

- **Build/test:** Create parallel state regions in an LVGL desktop simulator: session (`inactive/connecting/live/reconnecting`), input (`gated/quiet/user_speaking`), output (`idle/generating/playing`), plus battery/network/safety overrides and emotional accents. Show amber with uplink gated during connection, cyan only when capture actually flows, and off/private after local stop ([ADR 0008](../../../docs/decisions/0008_use_exactly_two_physical_controls.md): power-off is the hardware kill; there is no software `MUTED` state). Drive speaking motion from an audio-amplitude trace, preserve a cyan live indicator while output plays, render simultaneous user/assistant speech truthfully, and implement the sliding caption below the face — paced against a simulated playback cursor, trimmed on barge-in, legible at 2-inch scale.
- **Purchase/decision:** Buy nothing. Choose one face grammar (eye radius, blink timing, motion limits, type scale) for EVT rather than many themes.
- **Why:** Animation can be evaluated and unit-tested faster on desktop, and a state grammar prevents inconsistent one-off screens.
- **Exit evidence:** State-transition tests plus a 30 fps screen recording reviewed at actual 2-inch scale.

### Day 4 — Define the device protocol and observability

- **Build/test:** Specify versioned control events, binary audio framing, `device_id`, `binding_generation`, `setup_epoch`, `recovery_epoch`, `claim_nonce`, `conversation_id`, `session_epoch`, independent input/output sequences, `input_segment_id`, `response_id`, stable `output_id`, rendered sample count/rate, VAD, idempotent cancel/truncate, caption text deltas keyed to `response_id`/`output_id` (so truncation also trims displayed captions), configuration, per-direction backpressure, and health metrics. Define the gateway's output-to-provider `item_id`/`content_index` map and its cursor-to-`audio_end_ms` conversion. Sketch the companion-app contracts for generation/nonce-bound single-use claim tokens and rotating binding-recovery proof; binding-scoped app- and pager-origin `config_revision`/`If-Match` writes with mutation IDs; and expected-version history mutations plus `server_seq`, `oldest_available_seq`, and opaque cursors. The cloud may serve signed public carrier-preset metadata, but it has no endpoint for custom Wi-Fi/APN/authentication secrets or recovery secrets. Add end-to-end correlation and redact secrets/content from routine logs.
- **Purchase/decision:** Buy nothing. Decide that the device speaks only to our gateway with a revocable device credential.
- **Why:** A small stable protocol decouples firmware from provider changes and makes latency/failure diagnosable.
- **Exit evidence:** Protocol document/tests covering reorder, late chunks from an old generation, duplicate local/provider cancel races, `item_id`/`content_index` mapping, `audio_end_ms` conversion, render-boundary accuracy, separately timed provider acknowledgement/error, disconnect/session epochs, independent queue overflow, app- and pager-origin configuration conflicts/retries, expired history cursors, stale setup/binding generations, consumed claim nonces, and revoked credentials.

### Day 5 — Establish the software quality/latency gate

- **Build/test:** Run at least 50 timed desktop speech segments, a 100-utterance labelled endpoint corpus, and 100 scripted interruptions across the three evaluation scripts. The endpoint corpus covers 200–800 ms pauses, fillers, corrections, silence, nonspeech noise, and non-addressed background speech; classify early cutoff, missed endpoint, spurious response, and background-speech ambiguity. Compare the mini/full model on response usefulness, personality, speech-end-to-first-audio, speech-onset-to-output-stop, false interruption, and estimated cost. Break latency into local/provider endpointing, gateway, provider first audio, network, and playback buffering.
- **Purchase/decision:** Buy nothing. Keep or revise the default model with evidence; do not tune the hardware to mask service latency.
- **Why:** This establishes a ceiling on device performance and catches prompt/service problems before hardware arrives.
- **Exit evidence:** Results table; Gate A software passes when the conversation is useful, interruption works, VO-02c's endpoint-correctness limits pass, and no structural blocker prevents VO-02a's 1,200 ms median target. Keep 800 ms as a separately labelled stretch target, not a contradictory gate.

## Milestone 2 — Put the interaction on the ESP32-S3 mule

### Day 6 — Inspect and baseline the CoreS3 Lite

- **Build/test:** Photograph/record board revision and packaging, place an opaque cover over the built-in camera, omit its driver/clock initialization, update only through the vendor-supported path, and run display/touch/mic/speaker/Wi-Fi self-tests. Measure tethered idle/demo current only with the internal cell fully charged/stable or separately account for PMIC charging current.
- **Purchase/decision:** If shipment is delayed, continue simulator/gateway hardening; do not substitute impulsively. Return/exchange only for a reproducible hardware fault.
- **Why:** A known-good baseline distinguishes our bugs from delivery damage, board revision, or cable problems.
- **Exit evidence:** Inventory record, self-test results, board ID, toolchain version, and current baseline.

### Day 7 — Port the face and controls

- **Build/test:** Port the parallel state machine, persistent session indicator, sliding caption, and animation assets. Expose exactly one physical conversation control and one physical power control; the touchscreen may present status, volume, setup, and confirmation UI but does not add a physical switch/button. The conversation action requests a session: show amber with capture gated until authentication, then cyan as capture opens; the same action from connecting, reconnecting, or live stops locally. The product power action is a latching on/down switch. An ordinary claimed boot without the recovery chord returns to private idle; factory-first-boot and recovery enter capture-gated setup. When online, app-requested setup is accepted only as an authenticated current-owner app→gateway→pager command; when offline, setup entry is local through the touchscreen or eight-second power-on chord. A temporary mule input may stand in for either physical part until Day 12, but it is fixture-only and cannot satisfy acceptance. Measure action-to-face latency and frame time under deliberate CPU load.
- **Purchase/decision:** Buy nothing. Keep the camera disabled and retain the 2-inch screen for EVT.
- **Why:** The face must remain responsive independently of the cloud and audio path.
- **Exit evidence:** All local states at 30 fps, action response under 100 ms, no watchdog reset during a 30-minute animation soak.

### Day 8 — Validate concurrent audio and the AEC reference locally

- **Build/test:** Run CoreS3 capture and playback simultaneously at the initial 16 kHz AEC rate. Verify the ES7210 microphone lanes and speaker-feedback reference lane against the received-board schematic/reference code; map channels and measure reference polarity/delay, clipping, noise, and drift. Start ESP-SR with one microphone plus one reference in its low-cost full-duplex AEC mode; defer a second microphone and optional noise suppression/gain control until measured A/B tests. On barge-in, ramp output down and keep TX DMA feeding silence so shared I2S clocks and microphone RX remain alive. Record sample format, TDM slots, DMA buffers, gain, CPU/RAM, and safe speaker limits.
- **Purchase/decision:** If concurrent I/O and the reference lane are verified, order one relocatable acoustic-mule set for Day 12: compatible digital mic, I²S amp, 8-ohm speaker, illuminated conversation button, latching power switch, real switched-microphone gate plus hardwired indicator parts, and safe prototyping connectors/board. Confirm free I²S/GPIO, reference routing, and electrical compatibility first; otherwise buy nothing and document the blocker.
- **Why:** Network/model work cannot repair clipped capture, unstable shared clocks, or a missing/misaligned AEC reference. Early ordering keeps enclosure-specific AEC from becoming a late surprise.
- **Exit evidence:** Saved microphone/reference/output diagnostics, channel map and delay plot, conservative volume ceiling, 30-minute simultaneous-I/O run without overflow/underflow or missed AFE deadlines, at least 20% measured CPU headroom under this load, internal/DMA-memory low-water record, and any acoustic-mule receipt/ETA.

### Day 9 — Stream embedded audio in both directions

- **Build/test:** Send AEC-processed microphone frames while a known server stream plays, using independent bounded queues, generation IDs, sequence numbers, reconnect/backoff, and metrics. Make the gateway's initial 16↔24 kHz device/provider resampling explicit and measured. Inject delay, loss, late cancelled-generation chunks, and disconnects in either direction.
- **Purchase/decision:** Buy nothing. Choose initial codec/frame size from measured MCU load and latency, not bandwidth folklore.
- **Why:** Known audio separates embedded transport from model behavior.
- **Exit evidence:** One-hour duplex known-audio soak with documented underflows, overflows, resampler quality/load, stale-generation rejection, CPU/memory headroom, and reconnect time. This transport-only test does not substitute for the later provider-session-renewal test.

### Day 10 — Complete embedded full-duplex live voice

- **Build/test:** Connect the CoreS3 path to Realtime. One conversation-button action requests connection and shows amber with no microphone payload; authenticated readiness changes to cyan and opens capture. Microphone streaming then continues while returned audio plays; confirmed near-end speech clears that output generation and drives gateway cancellation/truncation. A second action from any full-duplex session state closes capture/playback locally even if gateway/provider work is stuck. If useful for diagnosis, measure a half-duplex developer-fixture path separately; do not expose it in the product state machine, app settings, or acceptance UI.
- **Purchase/decision:** Buy nothing beyond the Day 8 gated acoustic-mule order. If only half-duplex works, record Gate A as failed and reopen AEC/audio-front-end/compute work rather than weakening the target.
- **Why:** This is the smallest honest product loop for the intended interaction and tests the cancellation architecture with real render timing.
- **Exit evidence:** Recorded live session with at least ten exchanges and no per-turn press, successful speech barge-in with no stale resume and a correctly trimmed caption, explicit start/stop indication, caption first-render latency and caption/audio drift measurements, and correct parallel face states. Any half-duplex diagnostic result is labelled developer-only and cannot pass Gate A.

### Day 11 — Make cancellation and state synchronization boring

- **Build/test:** Hammer speech-during-output, double-talk, brief acknowledgements (which intentionally interrupt under the MVP policy), internal pauses/fillers/short corrections, missed and false local VAD candidates, repeated start/stop presses, stop-during-connecting/reconnecting/thinking/output, late generations, duplicate local/provider cancel events, playback-cursor reconciliation, caption-trim reconciliation with late transcript deltas, mismatched `content_index`, provider truncate timeout/error, gateway/provider transport outages shorter and longer than 10 seconds, gateway restart, and power-cut-during-live (no auto-resume on power-on). Add setup-state tests: unclaimed first boot enters capture-gated setup automatically; a claimed online pager accepts an app request only after the gateway authenticates the current account/binding and only while private-idle; offline entry uses the local touchscreen or holding the conversation button while sliding power on for eight seconds; the chord is ignored after boot and never transfers ownership by itself. Force reset, watchdog crash, bootloader entry, and interrupted/successful OTA while capture is requested and prove the capture-enable line and cyan indicator fail low until a fresh authenticated live-ready transition. Prove that every entry into `reconnecting` uses one non-extendable 10-second capture-reopen timer (NW-02c) regardless of cause, and define which state wins when power/offline/cancel/setup collide.
- **Purchase/decision:** Buy nothing. Lock precedence: power state and faults override connectivity, which overrides model expression accents.
- **Why:** Cute devices feel broken when their animation and audio disagree more than when an answer is imperfect.
- **Exit evidence:** Automated transition matrix and 100 randomized interaction sequences without stale playback.

### Day 12 — Validate the first enclosed acoustic and privacy path

- **Build/test:** Assemble the compatible acoustic/privacy parts ordered after Day 8 in a safe temporary enclosure: relocatable mic, amp/speaker, illuminated GPIO conversation button, synchronized render reference, a switched microphone rail/data gate with an electrically coupled indicator, and a latching hard-off path — bench instrumentation prototyping [ADR 0008](../../../docs/decisions/0008_use_exactly_two_physical_controls.md), not a product mute control. Bias capture-enable and cyan indication off in hardware through reset, crash/watchdog, bootloader, and OTA states; require firmware to earn enable only after authenticated live readiness. Isolate or block USB, debug-adapter, and modem back-power so shipping hard-off de-energizes capture and compute. Implement credential revocation, volatile-buffer clearing, diagnostic redaction, raw-audio non-retention, and opt-in/forget flows for structured server memory. Run simultaneous playback/capture, double-talk, scripted barge-in, assistant-only playback, hand/table scenes, and stop/reset/crash/OTA/power-cut/revocation fault injection; never ground either bridge-tied amplifier output.
- **Purchase/decision:** Buy nothing. If the gated parts have not arrived, take a shipping pause rather than opening Gate B without measured capture-gate evidence. Confirm no raw audio is retained by our service by default and no GPS/camera feature enters MVP.
- **Why:** The stock CoreS3 has no externally observable capture gate, and cellular spend should follow an initial enclosed AEC/privacy result rather than precede it.
- **Exit evidence:** Initial reference-delay/residual-echo and double-talk results, false/missed barge-in count, verified fail-low capture-enable/indicator coupling, storage/log inventory, packet trace showing no audio outside cyan full-duplex `LIVE`—and none during setup/recovery, reset/crash/OTA, or after stop, power-cut, or revocation—back-power measurements with USB/debug/modem paths attached, successful delete tests, and a signed Gate A interaction/privacy verdict.

## Track B — Companion app vertical slice (parallel sessions B1–B4)

Track B implements [ADR 0007](../../../docs/decisions/0007_use_companion_app_and_cloud_history_sync.md), the [detailed hybrid architecture](../../../docs/design/0002_companion_app_and_sync_architecture.md), and the companion-app requirements. Its sessions are project days that run in parallel with Days 6–20 (B1 can start once the Day 4 protocol sketch exists; B2 needs the physical CoreS3). Track B must fully pass before Gate C, because the immutable device identity/key, on-device one-time factory-bootstrap verifier, package QR containing only identity/bootstrap secret, runtime active-setup verifier, rotating binding-recovery verifier, and their secure lifecycle are manufacturing inputs to the carrier's production plan. It requires no hardware purchases.

### Day B1 — App skeleton, accounts, and gateway app API

- **Build/test:** Spike React Native as the candidate app shell (`src/app/`) with sign-in against the gateway's account service, plus thin native bridges to Espressif's maintained iOS and Android provisioning libraries. Define and stub the app-facing gateway API: claim-token issuance bound to expected `binding_generation` and a fresh `claim_nonce`; device/binding registry with `recovery_epoch` but no recovery secret; binding-scoped non-secret configuration reads and idempotent mutation-ID + `If-Match: config_revision` writes from either the authenticated app or pager; signed/versioned public carrier-preset metadata; and expected-version history mutations plus `server_seq`, `oldest_available_seq`, and opaque-cursor changes. Every configuration request carries `(account_id, device_id, binding_generation, origin)` and stale bindings cannot read or mutate it. No cloud endpoint accepts custom Wi-Fi passwords, custom APNs, cellular authentication credentials, or recovery secrets.
- **Purchase/decision:** Buy nothing. Evaluate the React Native/native-library bridge, permissions, foreground lifecycle, build maintenance, and licenses before freezing the stack; an unproven third-party React Native provisioning wrapper is not an architectural dependency.
- **Why:** Accounts and the claim-token API precede any BLE work, and stubbing the API first lets device and app sides develop against a contract.
- **Exit evidence:** App signs in, requests a generation/nonce-bound claim token, reads configuration, and handles app-origin, pager-origin, stale `config_revision`, stale `binding_generation`, and stale `recovery_epoch` conflicts without timestamp last-write-wins. Retrying one mutation ID has one effect; a new binding starts with history retention, retained-history context, and structured-memory consent off; the service contains no recovery plaintext; a signed carrier preset verifies; and history pages expose an opaque cursor plus `oldest_available_seq`. The bridge-risk note and API contract are versioned alongside the Day 4 device protocol.

### Day B2 — BLE provisioning end to end

- **Build/test:** Bring up `network_provisioning` over BLE with protocomm Security 2 (per-device salt/verifier), compiling out or explicitly rejecting Security 0/1 downgrade attempts. Support the standard Wi-Fi messages plus protected `/cell-config`, `/claim`, `/info`, and `/network-test` endpoints. On first unclaimed boot, advertise setup automatically with capture gated. For a claimed private-idle pager, an online app can open setup only by sending an authenticated request to the gateway, which validates the current binding and commands the pager; if offline, entry is local through the touchscreen network-repair flow or the exact recovery chord (hold conversation while sliding power on for eight seconds). Require foreground onboarding. Signed public carrier-preset metadata may be fetched by the app/cloud, but custom Wi-Fi/APN/authentication secrets travel only inside the protected BLE session and never through the gateway, logs, backup, or durable app storage. Keep provisioning alive until the pager redeems the claim token over TLS, disables first-claim bootstrap, generates/installs the new binding recovery verifier, delivers the recovery secret once, and receives bounded app save/acknowledgement; then atomically commit encrypted local state, clear every plaintext buffer, stop advertising, and release BLE memory. Interrupted delivery requires authenticated owner rotation, never redisplay. Measure that memory against the VO-09 floor and prove provisioning is unreachable during connecting/live/reconnecting.
- **Purchase/decision:** Buy nothing. Do not generalize this GATT surface into BLE audio, pairing, or accessory support; defer accessories to a separately threat-modelled task.
- **Why:** Provisioning is the app's riskiest embedded integration; doing it before the cellular gates means field tests (Day 13 onward) can onboard networks the product way instead of hardcoding credentials.
- **Exit evidence:** Fresh device provisioned and claim-acknowledged from each foreground app build in under two minutes; Security 0/1 and wrong-secret attempts fail; a sniffer/storage/log audit finds no plaintext network secret; interrupted/backgrounded onboarding resumes or restarts safely; RAM is measured; and state-machine tests prove setup is capture-gated and locked out during connecting/live/reconnecting.

### Day B3 — Claiming and cellular configuration

- **Build/test:** Implement the full claim flow. Manufacturing installs a one-time first-claim bootstrap salt/verifier on the pager; factory packaging carries only immutable device identity plus the corresponding bootstrap secret. Initial claim permanently disables the verifier, and no packaged proof can recover a later binding. The pager persists verifiers, so it never claims to redisplay an existing secret. Whenever setup needs an on-screen active secret, generate/show a fresh value once while atomically replacing its verifier and incrementing `setup_epoch`; any previous setup secret immediately fails. The signed-in app obtains a short-lived single-use token bound to account, device identity, `setup_epoch`, expected `binding_generation`, and fresh `claim_nonce`, sends it through `/claim`, and the pager redeems it using its factory TLS identity. The gateway atomically consumes token/nonce, binds the account, advances `binding_generation`, and issues a revocable device credential. The pager then rotates `recovery_epoch`, generates a binding-scoped recovery secret, installs only its verifier, and delivers the secret once inside Security 2 for explicit owner save/export; plaintext is erased after acknowledgement/timeout and interrupted delivery requires authenticated rotation. Claim, owner release, authorized recovery, and revoke atomically invalidate all outstanding tokens/nonces and prior recovery proof. Self-service transfer requires current-owner release. Account-loss transfer is server-authorized only after account verification and physical proof: following successful current-binding recovery proof over Security 2, the pager signs a fresh challenge/request ID, device and requested-account IDs, `setup_epoch`, `recovery_epoch`, expected `binding_generation`, current `claim_nonce`, and expiry with its immutable factory key. Recovery is bounded/audited and follows the frozen prior-owner notice/cooldown policy; neither support nor the boot chord may bypass those invariants, and no recovery secret reaches the gateway. On release or authorized recovery, the atomic transition compare-and-swaps generation/nonce/recovery epoch, advances them, revokes prior credentials/proof, and causes the pager to purge every prior-binding account identifier, credential, recovery verifier, cached context/configuration, pending mutation, Wi-Fi credential, and custom cellular/APN/authentication profile before accepting the new binding; only immutable factory identity remains. Implement signed public carrier presets plus validated advanced fields—custom APN, PDP type (`IPv4`/`IPv6`/`IPv4v6`), authentication (`none`/PAP/CHAP), optional username/password, and roaming—with custom values written through BLE-only `/cell-config`. Resale release requires physical-SIM removal/deactivation confirmation; lost-device revocation/account deletion direct carrier deactivation, and a future managed eSIM needs an explicit profile deactivation/transfer transaction.
- **Purchase/decision:** Buy nothing. Use a physical SIM with its PIN disabled for MVP and leave activation/billing in the carrier portal. Treat Starlink Direct to Cell only as a conditional participating-carrier coverage trial: require written confirmation of the target country, partner operator, SIM/plan, modem category/release, and bands; do not buy a Starlink terminal or invent a generic `Starlink` APN.
- **Why:** Claiming is the security boundary between "paired a phone" and "owns the device"; cellular config must exist before the Day 15–18 modem work needs an APN.
- **Exit evidence:** Claim/replay/steal/release/recovery/revocation matrix across setup, recovery, and binding epochs; proof verifier-only state never reveals a secret, setup/recovery rotation is atomic, claim nonces cannot replay, factory bootstrap fails after first claim, every prior-owner recovery code fails after rebind, and no recovery plaintext enters cloud/logs. Prove the recovery chord alone cannot reassign an owned device; release/authorized recovery purge prior-binding/recovery/network/cellular state before new-owner use while preserving only factory identity. Verify physical-SIM removal/deactivation UI for resale/loss/account deletion, signed-public-preset and custom-secret round-trips, and bounded non-secret modem errors. Record a qualified Direct-to-Cell test plan or an evidence-backed `not available for this carrier/country` result.

### Day B4 — History sync and retention controls

- **Build/test:** Implement the gateway as the single writer for opt-in, purgeable history content plus a server-ordered change stream keyed by globally unique event IDs and account-scoped `server_seq`; apps consume an opaque cursor and retries deduplicate by event/source/mutation ID. Every delete or other history mutation supplies its expected entity/version and receives either the next version or an explicit conflict. Every change page returns `oldest_available_seq`; content-free tombstones remain available through the maximum valid cursor age, which also covers every still-valid offline authorization lease, and `oldest_available_seq` must not advance past a deletion such a cursor could miss. A cursor older than that boundary forces authenticated full-snapshot reconciliation instead of silently skipping deletion. Store only finalized machine-transcript user text, finalized assistant text known to have been heard through the playback cursor (or an explicit interruption marker when the text boundary is uncertain), sanitized user-visible tool action/status/results, and timestamps—never raw input/output audio or arbitrary provider payloads. Encrypt the app cache with a device-bound Keychain/Keystore key, exclude it from OS/cloud backup, and require fresh authorization plus a full authoritative reconcile after reinstall, restore, account switch, lease expiry, or cursor expiry. Offline display uses a signed, installation-bound authorization lease with server issue/expiry and duration at most 24 hours, renewable only through authenticated server contact. Validate same-boot age with monotonic elapsed time plus wall time; wall-clock rollback or boot/time discontinuity without rollback-resistant platform time fails closed until contact. Test two app installations, duplicate/reordered delivery, offline mutations, cursor catch-up, clock rollback/reboot, sign-out/account switch, reinstall/restore, and deletion convergence; history never crosses BLE.
- **Purchase/decision:** Buy nothing. Make future retention default-off and not pre-checked. Turning saving off leaves previously retained history accessible and asks separately whether to keep or delete it. Item/conversation/all-history source deletion defaults to cascading derived-memory facts; an explicit per-fact confirmation may retain a separately confirmed fact. Account deletion has no keep/recompute branch: it unconditionally purges all structured memory. Account deletion is server-authoritative: show it as pending until acknowledged, advance device generations/nonces/recovery epochs, revoke sessions/devices/recovery proofs, purge server content, prompt carrier-SIM deactivation, and promptly clear online replicas. A disconnected pager purges its recovery verifier and network/cellular state when the definitive revocation response arrives. Truthfully state that an offline encrypted app cache cannot be remotely erased instantly; it becomes unreadable no later than its 24-hour authorization-lease expiry and is physically erased when the next server contact returns an authoritative deletion/revocation or revoked-credential response. Privacy copy must distinguish Mochi's durable storage from provider handling: verify the current OpenAI policy at release, disclose that API content may currently appear in abuse-monitoring logs for up to 30 days by default, and claim zero provider retention only if the account is approved and configured for the applicable control.
- **Why:** History is the app's user-visible payoff and the biggest privacy surface; it must be tested against the same gateway the pager uses, not a mock.
- **Exit evidence:** Retention-off and raw-audio storage audits; proof saved history remains readable when future saving is off; finalized/interrupted/tool-record fixtures; expected-version conflict and no-duplicate cursor traces; `oldest_available_seq`/tombstone/expired-cursor invariants; history-source deletions test both default derived-memory cascade and explicit confirmed-fact keep, while account deletion proves unconditional memory purge. Connected caches clear promptly; a deliberately disconnected cache locks on lease expiry/clock rollback/reboot and purges after a definitive server revocation response. Backup-exclusion and reinstall/restore full-reconcile tests, BLE traffic audit, reviewed provider/account-deletion copy, and a recorded walkthrough from onboarding to reading/exporting/deleting history complete the evidence.

## Milestone 3 — Test mobile networking, then decide on standalone LTE

### Day 13 — Screen the experience over a phone's mobile backhaul

- **Build/test:** Run a 30–60 minute full-duplex live session through a phone hotspot in strong and weak-but-usable coverage, including sustained simultaneous uplink/downlink and scripted barge-ins. Record the phone's carrier and 4G/5G radio access technology/band when exposed, plus RTT/jitter, endpoint/first-audio and interruption latency, false/missed interruption, reconnects, bytes per live minute, CPU/memory/current/temperature, and audio failures. Force LTE only if the phone/carrier exposes a supported setting; otherwise label the result accurately. On route loss, turn the indication amber, close uplink, discard raw/uncommitted input and queued output, reconnect/authenticate, reconstruct only committed items/settled tools, and reopen capture only after cyan `LIVE` returns within the 10-second NW-02c deadline. Test a longer outage: expiry must clear live intent/off and later recovery must require a fresh press. Provision the hotspot credentials through the Track B app flow rather than hardcoding them.
- **Purchase/decision:** Gate B opens only if Day 12's initial enclosed full-duplex/privacy gate passed, Wi-Fi voice is stable, cellular backhaul is acceptable, deployment region is confirmed, and standalone use is still valuable enough to justify cost/size. Otherwise keep hotspot-only and document why.
- **Why:** This cheaply screens user experience on one phone/carrier/location. It does not validate the target modem's LTE coverage, carrier acceptance, RF, power, GNSS, or embedded failover.
- **Exit evidence:** Comparison table for normal Wi-Fi versus cellular-backed hotspot, route/session trace, unresolved target-modem risks, and a signed Gate B verdict.

### Day 14 — Conditional cellular order

- **Build/test:** Recheck target carrier bands/model listings, seller stock, return policy, physical-SIM/service terms, APN/PDP/authentication/roaming requirements, supplied antenna list, and expected data volume. Confirm that the SIM PIN can remain disabled for MVP and that the current modem package includes one LTE MAIN and one GNSS antenna, then get seller confirmation for a compatible LTE AUX/diversity antenna and an adequately powered documented 5 V HAT supply/cable. Qualify a Direct-to-Cell option only through a participating mobile operator that confirms the exact country, SIM/plan, modem release/category, and bands; standard Starlink terminal service is not a pager path.
- **Purchase/decision:** If Gate B passed, order one returnable [SIM7600G-H HAT](https://www.waveshare.com/product/iot-communication/sim7600g-h-4g-hat.htm), one compatible AUX LTE antenna, and **one** low-cost SIM path—Soracom plan-US for a US test or a direct-carrier SIM, not both. Do not commit to a nonrefundable/high-cost plan before reading the received IMEI. Acquire a USB meter only for average energy and arrange access to a bandwidth-appropriate scope plus probe/shunt or power analyzer for modem-rail transients. Otherwise buy nothing.
- **Why:** Region, operator, and plan compatibility are part of the component—not paperwork after purchase.
- **Exit evidence:** Country/carrier/model/antenna/power compatibility notes, one chosen service path, instrumentation plan, receipts, or a written no-buy decision.

### Day 15 — Activate and enumerate the modem

- **Build/test:** With MAIN and AUX LTE antennas connected before power, use the documented 5 V HAT input from a source/cable with adequate margin. On a Linux development host over USB, identify modem interfaces, record firmware/IMEI securely, check exact model/IMEI acceptance, activate the single selected SIM/APN/service, attach to LTE, resolve DNS, and reach only controlled endpoints first. If using Soracom plan-US, its base allocation is only a tiny telemetry allowance; activate a sufficiently large permitted bundle before voice traffic.
- **Purchase/decision:** Only after acceptance, activate/buy the chosen 5–10 GB-equivalent service for one test month. Do not order production modules or more antennas. Resolve rejection with seller/carrier while return windows remain open.
- **Why:** Host, SIM, APN, firmware, and radio problems are easier to isolate on Linux than inside the pager.
- **Exit evidence:** Reproducible attach procedure, sanitized command/log transcript, assigned network path, and speed/latency baseline.

### Day 16 — Characterize coverage and reconnect

- **Build/test:** With the vendor-recommended MAIN+AUX configuration, measure RSSI/RSRP/RSRQ/SINR, RTT, attach time, cold boot, weak-signal behavior, cell change, and reconnection across several indoor/outdoor locations. Power off before connecting/disconnecting antennas. Use natural coverage or expert-controlled attenuation/shielding for weak-signal work—never transmit into an open MAIN port.
- **Purchase/decision:** Buy no antenna beyond the documented MAIN/AUX/GNSS setup until a controlled result defines a different need.
- **Why:** A single successful speed test says little about a mobile conversational product.
- **Exit evidence:** Location/test matrix and a ranked list of failure modes.

### Day 17 — Run realtime voice over standalone LTE

- **Build/test:** Route the established full-duplex gateway workload through the Linux/USB modem baseline for 30–60 minutes with simultaneous audio in both directions and scripted interruptions. Measure per-direction data, p50/p95 endpoint-to-first-audio and speech-onset-to-stop latency, jitter-buffer behavior, cancellation/truncation, reconnects, and carrier NAT/session behavior. Label this as a modem/network baseline, not embedded integration. If and only if Day 14 qualified a participating-operator Direct-to-Cell IoT service, run the same labelled workload there and compare coverage/latency/data limits; otherwise record it as unavailable rather than treating a normal terrestrial LTE result as a Starlink test.
- **Purchase/decision:** Select a provisional monthly data assumption from measured bytes/hour. Reject ultra-low-data plans that throttle or prohibit the workload.
- **Why:** Raw PCM arithmetic and codec claims are not a bill; actual protocol overhead, silence, retries, and tools matter. For scale: 16 kHz mono Opus at ~20–24 kbps is roughly 9–11 MB/hour per direction (ADR 0005 amendment), versus 173 MB/hour for raw PCM — measure which reality the transport actually delivers.
- **Exit evidence:** LTE versus hotspot/Wi-Fi report and projected light/medium/heavy monthly data.

### Day 18 — Prove embedded modem ownership, power, and heat

- **Build/test:** Connect the modem to the intended ESP32-S3 path and prove one exact transport (for example, high-rate UART/PPP with hardware flow control or a supported USB-host network class), including USB host/device ownership, independent programming/recovery, reset/power sequencing, compression/throughput, TLS, reconnect, and simultaneous face, AEC, I²S RX/TX, encrypted uplink, and encrypted downlink. A 115,200-baud UART cannot carry even one 384 kbit/s PCM direction. Separately measure CPU/RAM/queue headroom, average input energy, and modem-rail transient current with bandwidth-appropriate instrumentation during overlap, barge-in, weak signal, and reconnect; record temperatures against predefined datasheet-derived abort limits. Use the HAT's documented 5 V source—do not feed 3.4–4.2 V into its 5 V input or assume a laptop/thin cable/slow meter preserves bursts.
- **Purchase/decision:** Do not select the final battery and do not freeze a carrier if the embedded transport, USB roles, peak capture, supply margin, or thermal test is unresolved. If ESP32-S3 cannot own the path, reopen the compute architecture rather than adding an unbudgeted Linux companion.
- **Why:** Linux enumeration proves the modem, not the pager host. Host feasibility, brownouts, and heat constrain compute, interface, regulator, connector, battery, PCB, and enclosure together.
- **Exit evidence:** Working embedded encrypted voice path under concurrent load; interface/USB/debug decision; reset/reconnect trace; bandwidth/CPU/RAM numbers; scope/power-analyzer transient and average-energy traces; thermal log; preliminary rail requirements. If fast instrumentation is unavailable, mark peaks unverified and keep Gate C closed.

### Day 19 — Decide whether GNSS earns space

- **Build/test:** Test the SIM7600 GNSS outdoors, near a window, and indoors; record cold/warm time-to-fix, current cost, accuracy, and antenna coexistence. Write one concrete user flow that would use it safely.
- **Purchase/decision:** Default decision is omit/disable GNSS. Add a separate MAX-M10-class receiver only in a later task if the feature value and modem result justify it.
- **Why:** “Optional GPS” still costs antenna area, energy, privacy work, and certification complexity.
- **Exit evidence:** GNSS experiment plus keep/omit ADR proposal.

### Day 20 — Connectivity architecture freeze

- **Build/test:** Review full-duplex voice, network, data, embedded-host, USB-role/debug, power, thermal, carrier, region, GNSS, and reconnect evidence. Prove warm route loss reaches an authenticated transport within 15 seconds while amber/reconnecting emits no microphone payload. For route, gateway, and provider transport/session loss, prove capture resumes only when cyan `LIVE` returns before one non-extendable 10-second reconnect deadline; expiry clears live intent/off, and later recovery requires a fresh press. Separately measure cold attach. Freeze one exact modem transport, flow-control/reset/power interface, and no-replay policy for independent input/output generations. Either select an exact compact replaceable modem board or label revision A LTE as externally tethered to the 56 × 65 mm-class HAT; use the selected vendor board's documented antenna connectors rather than inventing a carrier RF path.
- **Purchase/decision:** Confirm Wi-Fi preferred plus modular LTE failover, or document a different evidence-based outcome. Purchase no full-5G or bare LGA module.
- **Why:** PCB work needs a proven host role, transport, session transition, and mechanical module—not interchangeable “USB/UART” labels or an enclosure assumption around a bench HAT.
- **Exit evidence:** Updated ADRs, interface control document, and remaining-risk register.

## Milestone 4 — Turn measurements into product geometry and a battery decision

### Day 21 — Build full-scale volume models

- **Build/test:** Make 95 × 60 × 30 mm and ~80 × 56 × 26 mm paper/foam blocks with actual compute/display/audio/battery mock volumes. Do not pretend the 56 × 65 mm-class SIM7600 HAT fits: model LTE as externally tethered unless Day 20 selected an exact compact replaceable board, in which case use its confirmed STEP/dimensions. Test one-hand hold, pocketing, lanyard, clip, button reach, and screen readability with several hand sizes if possible.
- **Purchase/decision:** Spend only on inexpensive foam/paper/adhesive already available; do not order a cosmetic print yet.
- **Why:** CAD without embodied scale hides thickness, finger occlusion, connector access, and assembly order.
- **Exit evidence:** Photos, dimensions, grip notes, and selected provisional envelope.

### Day 22 — Refine the acoustic mule against product geometry

- **Build/test:** Place Day 12's validated acoustic/privacy mule into temporary enclosures derived from Day 21's full-scale volume models. Refine speaker cavity/grille, gasket, mic-port position/separation, button feel and light visibility while preserving the synchronized reference and switched-microphone gate. Repeat simultaneous playback/capture, double-talk, scripted barge-in, assistant-only playback, hand/table/occlusion scenes, and safe-volume sweeps; never ground either bridge-tied MAX98357A speaker output.
- **Purchase/decision:** Buy only inexpensive enclosure iteration material. Do not freeze audio layout from the integrated CoreS3 or from Day 12's first temporary enclosure. Enforce an amplitude limit so a 5 V amp cannot overdrive a 1 W test speaker.
- **Why:** Day 12 establishes feasibility before cellular spend; this pass determines whether that path survives product-scale port spacing, cavity, gasket leakage, hand position, and control placement before carrier freeze.
- **Exit evidence:** Product-scale layout comparison, updated reference/delay characterization, residual echo and double-talk results, false/missed barge-in counts, chosen speaker/mic zones and duplex-volume ceiling, reverified capture-enable/indicator coupling, and a signed full-duplex acoustic-layout verdict.

### Day 23 — Close the power budget and choose a battery architecture

- **Build/test:** Combine measured device/audio/network/modem active and sleep modes into defined active/mixed-standby duty-cycle profiles, recording brightness, live-session minutes/hour, AEC duty, capture-only/playback-only/overlap time, route, and modem registration/power state. Include conversion efficiency, peaks, cold/aging margin, cutoff, charge time, and target runtime. Select candidate charger/power-path/regulator/gauge evaluation hardware, then—after any shipping pause—bench-test load steps, charge-and-run/load sharing, thermal limits, cutoff, and recovery. Start with a battery simulator/current-limited source and pouch cell disconnected; verify polarity, charge voltage/current, NTC policy, and load sharing before attaching a protected cell under observation.
- **Purchase/decision:** Only now buy one evaluation set and one traceable protected, tabbed/connectorized candidate cell if the datasheets and test plan pass review. Do not solder directly to a pouch/can. A protected cell without a thermistor still requires external product temperature policy.
- **Why:** Capacity, charger, regulator, and thickness should follow measured load behavior. Putting an unvalidated power circuit directly on revision A converts a debuggable module test into a board-and-battery safety risk.
- **Exit evidence:** Signed power tree/budget and duty profiles, candidate datasheets, bench traces for representative modem load steps/charge-and-run/cutoff/recovery, predefined abort temperatures, safe peak margin, and active/standby estimates.

## Milestone 5 — Design and order the modular carrier

### Day 24 — Capture the carrier schematic

- **Build/test:** Only after Day 23's power gate, draw a four-layer carrier containing the exact validated power path/charger/gauge; exact compute/display/touch interfaces; synchronized microphone capture, speaker render, and documented post-amplifier analog and/or rendered-digital AEC reference; illuminated conversation control; the power slide switch; and a hardware-default-low capture-enable net driving both the microphone gate and cyan indicator through reset/crash/bootloader/OTA ([ADR 0008](../../../docs/decisions/0008_use_exactly_two_physical_controls.md)). Make shipping hard-off isolate or block battery, USB, debug, and modem back-power paths while preserving an explicit safe development procedure; include resolved USB host/device plus independent debug/recovery, exact modular cellular transport, ESD/protection, and current measurement options. Add labeled low-speed audio/reference test points; use reviewed impedance-safe inline/probe structures rather than ordinary stubs on USB differential pairs or RF.
- **Purchase/decision:** Select parts by exact manufacturer number, lifecycle, authorized availability, package risk, and alternates. Do not order boards or bulk parts.
- **Why:** A complete BOM and power intent are prerequisites for useful review and quotation.
- **Exit evidence:** ERC-clean schematic, power tree, interface table, preliminary BOM, and open-issue list.

### Day 25 — Review the electrical design adversarially

- **Build/test:** Review every voltage, boot strap, connector direction, polarity, protection path, regulator transient/thermal limit, charge condition, fail-low capture-gate state, hard-off isolation/back-power path, USB role, audio clock, and modem sequence. Simulate only the power/analog questions the model can represent.
- **Purchase/decision:** Replace risky/no-stock parts on paper; avoid paying for a board to discover a searchable datasheet error.
- **Why:** ERC checks syntax, not engineering intent.
- **Exit evidence:** Closed review checklist, annotated datasheets/reference circuits, and zero unexplained ERC waivers.

### Day 26 — Lay out and mechanically co-design the board

- **Build/test:** Place from enclosure, antenna, speaker cavity, mic path, buttons, USB, battery, and assembly order. Preserve a ground plane, route current loops and high-speed lines correctly, add keep-outs and appropriate low-speed/impedance-safe probe structures, import exact STEP models, and print the board 1:1.
- **Purchase/decision:** Buy nothing. Choose the stack-up only against a named fabricator capability and live constraints.
- **Why:** Layout is an electrical/mechanical design, not automatic wire packing.
- **Exit evidence:** DRC-clean layout, 3D interference review, 1:1 physical overlay, and peer/RF checklist.

### Day 27 — Run DFM and compare landed quotes

- **Build/test:** Export and independently inspect Gerber/drill/BOM/CPL/assembly files. Request quotes from JLCPCB plus at least one of PCBWay, MacroFab, or Seeed. Ask about substitutions, stencil/setup, inspection/X-ray, electrical test, shipping/duty, and lead time.
- **Purchase/decision:** Select a supplier only on total landed cost and risk. Do not let a $2 bare-board promotion hide PCBA costs.
- **Why:** Supplier capability and substitutions are part of the design.
- **Exit evidence:** Manufacturer DFM feedback resolved, comparable quote table, exact released source tag/hash, and purchase recommendation.

### Day 28 — Gate C order

- **Build/test:** Conduct a final readiness review: exact compute/display/touch/audio/AEC-reference/capture-enable/power-switch/connectors and USB/debug roles are frozen; capture fails low through reset/crash/bootloader/OTA and hard-off blocks every USB/debug/modem back-power path; full-duplex acoustic and concurrent-load gates pass; Track B (provisioning, claiming, history) has passed so per-device identity, setup/recovery, binding, cache, and replica-lease behavior are defined manufacturing/service inputs; one embedded modem transport and its external/compact mechanical status are explicit; measured load steps trace to validated power choices; no unresolved safety/RF/mechanical blocker remains; test procedure exists; and all order previews match the release.
- **Purchase/decision:** If Gate C passes, order 5–10 assembled four-layer carriers plus two bare boards and only their required prototype parts. Order one low-cost enclosure print only if CAD uses confirmed component models. If it fails, order nothing and schedule the missing experiment.
- **Why:** Small quantity supports rework/yield learning without turning revision A into inventory.
- **Exit evidence:** Signed gate checklist, saved order configuration/receipt, released manufacturing package, or explicit no-buy remediation.

### Shipping pause — no project-day charge

Use supplier lead time to improve tests and fixture software. Do not quietly redesign the ordered revision; branch changes for the next spin and preserve the release exactly.

## Milestone 6 — Bring up, verify, and decide the next spin

### Day 29 — Build diagnostics and the fixture before boards arrive

- **Build/test:** Create a deterministic test image/procedure for rail checks, board ID, the conversation button/indicator and fail-low capture-enable net, reset/crash/bootloader/OTA states, the latching power switch, USB/debug/modem back-power isolation, display/audio buses, modem interface, current, and serial-numbered results. Separate production code under `src/` from fixture/developer code under `tools/`.
- **Purchase/decision:** Buy only low-cost pogo pins/cables/adapters called out by the reviewed test plan.
- **Why:** Testability designed before failure produces faster, less destructive bring-up.
- **Exit evidence:** Dry-run test sequence on the mule and a results schema.

### Day 30 — Incoming inspection and unpowered tests

- **Build/test:** Photograph packaging/boards, reconcile BOM substitutions, inspect polarity/joints/bridges under magnification, measure shorts/resistance from each rail to ground, and compare one bare board to files.
- **Purchase/decision:** Do not power a suspicious board. Open supplier issues within the claim window with evidence.
- **Why:** Current limiting cannot protect every reversed or shorted component.
- **Exit evidence:** Serialized inspection sheet and disposition for each board.

### Day 31 — Incremental powered bring-up

- **Build/test:** Set datasheet-derived abort limits and begin with the pouch cell disconnected. Use a battery simulator/current-limited bench source; validate polarity, rails, charge voltage/current, NTC behavior, load sharing, and sequencing one at a time. Then add reset/boot, independent debug/recovery, compute, controls, display, audio, and finally the modular modem. With battery, USB, debug, and modem paths exercised one at a time, verify hard-off cannot back-power compute/capture and reset/crash/bootloader/OTA all hold capture-enable low. Attach a protected cell only after the charger path passes and under attended observation. Record rework rather than hiding it.
- **Purchase/decision:** Replace only diagnosed parts. Avoid broad reorders until common-mode versus one-board faults are known.
- **Why:** Incremental power localizes faults and protects scarce assemblies.
- **Exit evidence:** At least two boards reach the same documented baseline with fail-low capture and hard-off isolation measurements, or a root-caused blocking defect is recorded.

### Day 32 — Run integrated voice/network soak

- **Build/test:** Run a button-opened full-duplex acceptance session over Wi-Fi/hotspot and, if fitted, LTE. Exercise spontaneous and scripted barge-in, double-talk, at least 60 assistant-speaking minutes for false-trigger measurement, conversation-button stop, latching power-switch cut with USB/debug/modem attached, fail-low reset/crash/bootloader/OTA paths, caption pacing and trim, first-boot/online-gateway-authorized-app/offline-touchscreen/boot-chord setup, provisioning lockout while live, AP loss/failover, gateway restart, late cancelled-generation packets, low battery, OTA rollback, and a 65-minute concurrent voice/animation/caption/AEC soak that renews the provider session before its current 60-minute limit. In parallel, exercise binding-scoped app- and pager-origin stale `config_revision` writes and idempotent retries; claim nonce/generation invalidation; and default-off history opt-in, expected-version conflicts, `oldest_available_seq` full reconciliation, offline delete/account-delete lease behavior including clock rollback/reboot, derived-memory default-cascade/explicit-keep plus unconditional account-delete purge, two-app convergence, and reinstall/restore against the same gateway.
- **Purchase/decision:** Buy nothing. Treat unstable behavior as data for the next spin, not a reason to add unreviewed modules.
- **Why:** Integration failures often appear only with concurrent radio, display, audio, and power loads.
- **Exit evidence:** Pass/fail matrix, endpoint early-cutoff/miss/spurious-response counts, acoustic/barge-in/false-trigger counts, provider-renewal trace, endpoint/interrupt latency, render-boundary accuracy, provider truncate acknowledgement/error timing, per-direction queue/reconnect/current traces, zero stale-output evidence, no missed AFE deadlines, at least 20% worst-case CPU headroom, internal/DMA-memory floor evidence, fail-low capture/back-power traces, no custom network secrets outside the local provisioning path, no raw audio/history over BLE, converged binding/configuration/history/memory/deletion traces, and defects with reproduction steps.

### Day 33 — Mechanical, battery, and thermal field trial

- **Build/test:** In the safe prototype enclosure, run desk/hand use, speaker/mic occlusion, attended charge/use, low-signal heat, and battery rundown. Do not perform body-worn/pocket LTE transmission until the RF-exposure plan establishes permitted antenna separation; use a fixture at the module/antenna's documented distance. Perform initial controlled short-drop trials with an inert battery mass, never while charging. Inspect after impact and retire any cell with denting, puncture, swelling, torn wrap/pouch, leakage, odor, or abnormal heat.
- **Purchase/decision:** Do not buy a larger battery to conceal efficiency or sleep bugs. Change capacity only through the measured power budget.
- **Why:** A bench-tethered success does not validate a carried product.
- **Exit evidence:** Runtime curve, temperatures, mechanical/acoustic observations, photographs, and safety disposition.

### Day 34 — Product acceptance demonstration

- **Build/test:** Record a reproducible live-session demo with exactly two physical controls: one conversation-button press shows amber connection with no uplink and then cyan listening, at least ten exchanges occur without per-turn presses, the user interrupts assistant speech by speaking, parallel face signals remain truthful, and a second press stops locally; the latching power switch cuts the device without USB/debug/modem back-power and power-on does not auto-resume. Also demonstrate fail-low capture through reset/OTA, the sliding caption tracking assistant speech and trimming on interruption, foreground BLE first-boot provisioning and claim, online gateway-authorized app setup, offline touchscreen setup, stop-during-connecting, the eight-second power-on recovery chord with capture gated, failed unauthorized reclaim/nonce replay, authorized recovery with prior-binding/network/cellular purge, physical-SIM release handling, Wi-Fi/hotspot, optional LTE, and app-/pager-origin `config_revision` conflict handling. With history explicitly opted in, show finalized/heard conversation content converging to a second/restored app, retained history still readable after future saving is disabled, expired-cursor full reconciliation, history-source deletion with derived-memory default-cascade/explicit-keep, unconditional account-delete memory purge, and honest offline-replica lease behavior under expiry/clock rollback/reboot. Show that raw audio, custom network secrets, and history never traverse the wrong channel. Run the measurable MVP requirements and publish honest misses.
- **Purchase/decision:** Buy nothing. Decide whether the concept merits another EVT spin based on evidence, not video polish.
- **Why:** A shared acceptance script converts a charming prototype into a comparable product iteration.
- **Exit evidence:** Demo video, requirements matrix, test artifacts, known-issues list, and cost snapshot.

### Day 35 — Retrospective and next architecture decision

- **Build/test:** Compare plan versus actual time/cost, identify the largest latency/power/acoustic/RF/manufacturing risks, and rank the next experiments. Update BOM availability and archive receipts/source releases.
- **Purchase/decision:** Choose one next path: revise the audio/compute/acoustic architecture if full duplex missed its gate; revise the modular carrier; begin an integrated LEXI-R10-class North American RF design with professional review; or stop/pivot. Still do not buy 5G unless the LTE evidence opens its gate.
- **Why:** A deliberate decision preserves learning and prevents sunk-cost escalation.
- **Exit evidence:** `retrospective.md`, updated requirement results, new/superseding ADRs, and a narrowly scoped `task_0002` proposal.

## Decision rule for schedule changes

If a day uncovers a safety, credential, power-integrity, region/carrier, or irreversible manufacturing uncertainty, stop the dependent purchase and add the smallest experiment that resolves it. If a day merely exposes normal software defects, fix and measure them without expanding the product scope. The objective is not to finish on Day 35 at any cost; it is to finish with trustworthy evidence and a safe next decision.
