# ADR 0007 — Use a companion app with BLE provisioning and opt-in cloud history sync

Status: Accepted for EVT
Date: 2026-08-31

## Context

The product owner requires a separate mobile app that connects to the pager over Bluetooth, lets the user enter Wi-Fi SSID/password, configures cellular ("4G information"), and holds conversation history, with app↔pager synchronization over either P2P/BLE or a central server. No prior record covered this; NW-05 said only "BLE is sufficient for provisioning" without naming a protocol, a security scheme, a claiming flow, or a history home.

Facts observed 2026-08-30/31: ESP-IDF 6.0 removed the `wifi_provisioning` component from core; its successor is the `espressif/network_provisioning` managed component (v1.2.4), with `wifi_prov_*` APIs renamed to `network_prov_*` (some gaining a `wifi_` infix, e.g. `network_prov_mgr_is_wifi_provisioned`). Protocomm Security 2 uses SRP6a plus AES-GCM and is Espressif's recommended production scheme. Security defaults have differed across IDF/component releases, so the product cannot rely on a default. Official Android and iOS provisioning libraries support Security 2. The Improv Wi-Fi BLE standard defines no protocol-level encryption or authenticated key exchange, carries only SSID/password, and has no official iOS SDK. Espressif estimates that keeping BLE provisioning active costs roughly 110 KB of runtime RAM, which argues for a bounded foreground commissioning state rather than an always-on synchronization link.

## Decision

Build one companion app for iOS and Android, and treat it as the second client of the ADR 0003 gateway.

**Provisioning.** Use ESP-IDF unified provisioning over BLE via the `network_provisioning` component with protocomm Security 2 and unique per-device proof-of-possession material written at manufacturing. Manufacturing installs the salt/verifier on the pager and prints only device identity plus the corresponding single-use bootstrap secret in the package QR for first unclaimed setup; initial claim permanently disables that verifier. Keep a separate active-setup salt/verifier; a new on-screen setup secret atomically rotates it with `setup_epoch`, because a verifier cannot regenerate a forgotten secret. Each claim/new binding also creates a fresh binding-scoped recovery secret, stores only its verifier with `recovery_epoch`, delivers it once over Security 2 to the new owner for explicit save/export, and invalidates every prior binding proof. Explicitly compile out or reject Security 0 and Security 1 in both firmware and app; do not inherit an SDK default. In the same encrypted session, add schema- and length-bounded custom endpoints: `/cell-config` (local APN profile), `/claim` (gateway claim token), `/info` (non-secret firmware/network status), and `/network-test`. Values are never logged or readable back. Provisioning runs only in a time-bounded setup/recovery state while capture is gated, never during a connecting, live, or reconnecting conversation. The app must remain foregrounded through the transaction, and BLE is shut down afterward so its approximately 110 KB runtime cost is released. Reject Improv BLE and a from-scratch GATT service because neither meets this authenticated, extensible contract as directly as Security 2. BLE is the sole MVP commissioning transport: generic Wi-Fi Direct is not part of this stack, and SoftAP is deferred unless recovery evidence justifies adding it behind the same setup gate and application-layer Security 2.

**Claiming and recovery.** The user signs into the app first. A factory-fresh pager automatically opens capture-gated setup. A claimed pager may reopen a short setup window from its touchscreen while private-idle. The app can request that window only when the pager is online: an authenticated app→gateway command causes that specific private-idle pager to advertise BLE locally. An offline phone cannot wake a BLE stack that is normally off. Offline recovery uses the boot-only chord in [ADR 0008](0008_use_exactly_two_physical_controls.md): hold the conversation button while sliding power on for eight seconds. A static unit QR may carry device identity and the one-time initial bootstrap proof, but the active setup screen also supplies a fresh, expiring challenge bound to that setup epoch. The factory bootstrap is disabled after first claim, and claimed-device recovery requires the current rotating binding proof, so a photographed factory or prior-owner code cannot authorize later recovery.

After the Security 2 channel is established, the signed-in app obtains a short-lived, audience-bound, single-use claim token bound to the account, immutable device identity, `setup_epoch`, expected current `binding_generation`, and server `claim_nonce`, then writes it to `/claim`. The pager redeems it over TLS using its factory identity. The gateway atomically compares generation/nonce, invalidates all outstanding claim tokens, rotates the nonce, binds the device, advances `binding_generation`, and rejects credentials, streams, or retries from an older generation. Claim, release, recovery, and revoke all rotate the nonce, so an unused old token cannot survive an ownership race. Replays, claims against an already owned unit, and expired/setup-epoch/generation/nonce-mismatched tokens fail without exposing account data.

An unprotected local gesture never transfers ownership. The current owner releases the device in the app. The boot chord plus the current binding's recovery secret may repair local networks, but an owned unit remains unclaimable. For account-loss transfer, a server-side account/support recovery requires both account authorization and physical proof: after the app proves that recovery secret over Security 2, the pager signs a fresh server challenge/request ID, device and requested-account IDs, `setup_epoch`, `recovery_epoch`, expected `binding_generation`, current `claim_nonce`, and expiry with its immutable factory key. Requests are bounded, audited, notify the existing account, and use a policy-defined expiry/cooldown when contact remains possible; numeric values and support authority must be frozen before Gate C. The atomic transfer compare-and-swaps generation/nonce/recovery epoch, invalidates tokens and the old recovery proof, advances all three, revokes old streams, and resets new-owner history/memory consent to off. On observing release or the new generation, the pager closes any live session and purges old binding credentials, working context, captions, media queues, volatile transcripts, config cache, prior recovery verifier, and the prior owner's locally stored Wi-Fi and custom cellular/APN/authentication profile before re-entering capture-gated setup; immutable factory identity remains. The new binding receives a new one-time-delivered recovery secret. The prior owner's cloud history stays in that account. Wi-Fi passwords, custom APNs, PDP-auth credentials, and any future SIM PIN never touch Mochi's cloud.

**Cellular configuration.** "4G information" for this hardware class is a provider profile: APN, IP/PDP type, optional PAP/CHAP username/password, roaming permission, and enable flag (`AT+CGDCONT`/`AT+CGAUTH` on SIMCom-class modems). Public, signed carrier-preset metadata may ship in the app/pager or be downloaded from Mochi cloud; it is not a credential. User-entered/custom APNs, derived profiles, and authentication values remain memory-only in the app, travel over BLE, and live only in the pager's protected credential store. The app discards those values after the pager acknowledges the write.

MVP uses an activated physical SIM with its PIN disabled. Cloud release cannot revoke the subscriber credential on that card: resale release requires explicit confirmation that the SIM was removed or carrier-deactivated, and loss/account deletion direct the owner to deactivate it in the carrier portal. Later PIN support must either prompt after every cold boot or securely persist the PIN; "use once and never store" cannot unlock a power-cycled modem. Do not build a generic consumer SGP.22 eSIM flow. SGP.32 IoT eSIM may be evaluated later with a compatible modem/eUICC, carrier, and eSIM IoT remote manager and must add an explicit profile deactivation/transfer workflow; it is an ecosystem decision rather than an app text field. Standard Starlink remains an external dish/router whose Wi-Fi the pager may use. Direct to Cell is a possible participating-carrier coverage path for compatible Release-10-or-newer Cat-1/Cat-1-bis/Cat-4 hardware and bands, not a universal `Starlink` profile or MVP dependency; [ADR 0002](0002_use_wifi_first_and_4g_lte_failover.md) defines its validation gate.

**Non-secret settings synchronization.** The gateway owns one ordered configuration document scoped to `(account_id, device_id, binding_generation)` and containing monotonic `config_revision`, volume, model/voice profile, prompt-profile version, history consent, and the separate memory consent. App and pager mutations carry `client_mutation_id`, the current binding generation, and `If-Match: config_revision`; the gateway either commits the next revision or returns the current document as a conflict. Claim, transfer, or recovery creates a fresh binding document with history and memory consent off and rejects every older-generation write. The pager clears prior binding-scoped preferences, applies the new defaults, and acknowledges ordered revisions. A touchscreen volume change may apply locally offline but remains pending with its base revision; on conflict the gateway document wins and the pager shows the resolution. Consent changes do not take effect until server commit. Neither client clocks nor last-writer-wins merge decide conflicts. Capture state is never remotely writable: the app cannot start a listening session. Custom network credentials remain outside this document and BLE-only.

**Conversation history.** History is a gateway/cloud-account feature, never a BLE/P2P feature. The gateway is its only durable writer and source of truth; the pager stores no history, and the app keeps only an encrypted authenticated cache. Under an explicit "Save conversation history" opt-in — **default off** and separate from the structured-memory opt-in — the gateway may enable machine input transcription even when user captions are hidden, then transactionally commits user-visible finalized items and an outbox/change record. Raw audio is never retained by Mochi by default.

Every record carries `account_id`, `device_id`, `binding_generation`, UUIDv7 `conversation_id`, gateway-assigned globally unique `history_event_id`, `session_epoch`, provider/device `source_item_id`, account-scoped gateway-assigned monotonic `server_seq`, record `version`, kind/role, finalized machine-transcript text, creation time, and interruption metadata. Before assigning the event ID, the gateway deduplicates source commits on `(device_id, conversation_id, session_epoch, source_item_id, kind)`; phone clocks never order changes. Tool history contains only a user-visible action/status and sanitized result, never arbitrary provider payloads or secrets. For interrupted assistant speech, retain only the reliably heard text prefix; if audio/caption alignment cannot establish that boundary, store an interruption marker without presenting the full generated suffix as heard.

Apps fetch changes after an opaque server cursor and use push/stream notifications only as invalidations before the same cursor fetch. The server publishes `oldest_available_seq`, retains content-free tombstones through the maximum valid cursor age, and rejects any older cursor; that client must authenticate and full-reconcile before showing restored cache. This binds cursor validity to tombstone retention so a long-offline or restored client cannot resurrect deleted content. Delete-item, delete-conversation, and delete-all mutations carry a stable `client_mutation_id` and expected record version, making retries idempotent and stale edits detectable. Turning future retention off is separate from deleting existing history, and retained history remains accessible while future saving is off. Releasing a pager does not implicitly delete its prior owner's retained history, but a new binding can never query it. Offline mutations remain visibly pending until server acknowledgement, and switching accounts immediately evicts the prior account's cache. Structured-memory facts carry their source event IDs; deleting those sources cascades by default, while keeping a separately confirmed fact requires an explicit choice.

The encrypted cache is account-scoped. Its database key is device-bound/non-synchronizing in iOS Keychain or non-exportable Android Keystore-backed storage where supported; authentication tokens use the corresponding secure store, and both cache and key are excluded from OS cloud/device backup. A restored cache is never displayed before authentication and full reconciliation. Offline history display requires a signed, installation-bound authorization lease with server issue/expiry and duration of at most 24 hours, renewable only through authenticated server contact. Same-boot validation uses monotonic elapsed time plus wall time; clock rollback or boot/time discontinuity without rollback-resistant platform time fails closed until contact.

**Account deletion.** Re-authenticated, confirmed deletion immediately revokes and unbinds devices at the gateway, advances their generations/nonces/recovery epochs, closes streams, cancels exports, and deletes Mochi account/config/history/memory content under the published server-side SLA. Connected apps purge caches. A disconnected app cannot be remotely wiped: it may display cache only until the current authorization lease expires, then locks it and erases it on the next server contact that returns an authoritative deletion/revocation or revoked-credential response. Offline pagers are unauthorized at the gateway immediately and, on reconnect, purge binding/recovery state plus local Wi-Fi/custom cellular credentials before capture-gated setup. Privacy copy distinguishes these replica timings, the required carrier-SIM action, and the separately configured provider-retention boundary.

This app history policy covers Mochi-controlled storage, not all provider processing. OpenAI states that API data is not used for training unless the customer opts in, but default abuse-monitoring logs may retain content for up to 30 days; eligible customers may apply for Modified Abuse Monitoring or Zero Data Retention. `/v1/conversations` retains application state until deletion and is not Zero Data Retention eligible, so it is not used as Mochi's product database. User-facing privacy copy must describe the actual approved provider data-control configuration rather than promising zero provider retention. The app↔pager BLE channel carries provisioning and bounded diagnostics only—never conversation content or live audio.

**App stack.** React Native is the cross-platform UI candidate, with thin native bridges to Espressif's maintained iOS and Android provisioning libraries as the authoritative Security-2 implementation. A third-party React Native wrapper may accelerate a spike but is not an architectural dependency until custom endpoints, current Security 2, foreground/background behavior, licensing, and failure recovery pass on both platforms. App source lives in `src/app/`.

## Why

- Security 2 gives a possession-proof key exchange and authenticated encryption with maintained first-party phone libraries; Improv would force plaintext credentials and a custom iOS implementation.
- Cloud history matches how the data already flows (device → gateway → provider). BLE history sync would add a phone-proximity dependency exactly when cellular independence is the point, and the pager deliberately stores no durable history to synchronize.
- Default-off retention preserves the documented privacy stance while satisfying the history requirement for users who want it.
- A claim-token flow, `binding_generation`, and an authenticated transfer/recovery process keep the gateway authoritative over device identity and revocation instead of trusting whatever phone happens to pair.

## Consequences

- The gateway grows a second authenticated client type, account binding generations, optimistic configuration revisions, a transactional history store/change feed, and deletion propagation; these need duplicate, replay, offline, multi-app, and account-switch tests.
- Manufacturing must provision a hardware-protected unique device identity/key and single-use factory-bootstrap verifier. Active-setup and binding-recovery verifiers are generated/rotated at runtime; printed bootstrap material is permanently disabled after first claim and is never a later owner-recovery credential.
- The IDF 6.x rename means pre-6.0 provisioning examples must be read with the `network_prov_*` translation.
- History retention becomes a user-visible toggle whose off state must be honest: Mochi creates no durable transcript when it is off, while provider retention is disclosed separately according to the account's data-control configuration.
- Network credentials cannot be edited remotely through the cloud; the user and phone must be near the private-idle pager for BLE commissioning.
- The 35-day plan gains a parallel companion-app track that must pass before Gate C freezes the carrier (claiming affects manufacturing data).

## Revisit when

Revisit if Security 2 or the Espressif phone libraries stop being maintained, if account-service requirements outgrow the gateway, if a phone-absent onboarding path becomes a support burden worth adding, or if users demand end-to-end-encrypted history, which would foreclose server-side search and memory features for locked items.
